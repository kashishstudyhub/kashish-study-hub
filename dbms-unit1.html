1. Database Approach

The database approach is a method of managing data in which related data is stored in a centralized or logically integrated database and is managed by a Database Management System (DBMS).

Main Features

  • Data is centrally managed.
  • Multiple applications can share data.
  • Data redundancy can be controlled.
  • Data security can be implemented.
  • Integrity constraints can be applied.
  • Backup and recovery mechanisms can be provided.
Example:

In a college database, student information can be used by the admission, examination and library systems instead of maintaining completely separate copies of the same information.

2. Traditional File System

In a traditional file-processing system, data is generally stored and managed in separate files by individual applications.

Problems of Traditional File Systems

  • Data redundancy
  • Data inconsistency
  • Difficult data sharing
  • Limited centralized security
  • Program-data dependence
  • Difficult concurrent access management
  • Backup and recovery challenges

3. Traditional File System vs DBMS

Traditional File System DBMS
Data is maintained in separate files. Data is managed through a database system.
Data redundancy may be high. Redundancy can be controlled through database design.
Data sharing is more difficult. Authorized users can share database data.
Security may depend heavily on applications. DBMS provides access-control mechanisms.
Relationships may need application-level handling. Relationships can be represented in the database.
Recovery may require separate mechanisms. DBMS can provide recovery facilities.

4. Data Models

A data model is a collection of concepts used to describe the structure of a database, relationships among data and constraints.

Types of Data Models

1. Hierarchical Model

Data is organized in a tree-like structure using parent-child relationships.

University
↓
Department
↓
Student

2. Network Model

The network model represents data using records connected through relationships. It can represent more complex connections than a simple tree.

3. Relational Model

Data is represented using relations, commonly called tables. Tables contain rows and columns.

4. Object-Oriented Model

Data is represented as objects containing data and associated behavior.

5. Schema

A database schema is the overall logical design or structure of a database.

It describes tables, attributes, relationships and constraints.

Example: 
STUDENT(
    RollNo,
    Name,
    Course,
    Marks
)

The structure above represents a possible schema for a Student relation.

Remember:

Schema = Structure/design of the database.

6. Database Instance

A database instance is the actual collection of data stored in the database at a particular moment in time.

Example

RollNo Name Marks
101 Rahul 85
102 Priya 90

The structure of this table is part of the schema, while the actual rows currently stored are part of the instance.

Easy Trick:

Schema = design
Instance = data at a particular time

7. DBMS Architecture

The three-level architecture separates user views from the logical database structure and physical storage details.

Three Levels

Level Description
External Level Describes the database view presented to a particular user or application.
Conceptual Level Describes the overall logical structure of the database.
Internal Level Describes physical storage of data.
External Level
↓
Conceptual Level
↓
Internal Level
↓
Physical Storage

8. Data Independence

Data independence is the ability to change the schema at one level without requiring changes at the next higher level.

1. Physical Data Independence

Changes to physical storage should not require changes to the conceptual schema.

Example: Changing storage organization or indexes without changing the logical database design.

2. Logical Data Independence

Changes to the conceptual schema should have minimal impact on external views or application programs.

Example: Adding a new attribute to the logical database without unnecessarily changing existing user views.

10. DBA and Database Designer

Database Administrator – DBA

A Database Administrator is responsible for administration and management of the database system.

Major Responsibilities

  • Database security
  • User authorization
  • Backup and recovery
  • Performance monitoring
  • Storage management
  • Database maintenance

Database Designer

A database designer designs the structure of the database based on the requirements of an organization.

Major Responsibilities

  • Identify entities.
  • Identify attributes.
  • Identify relationships.
  • Design database schema.
  • Define appropriate constraints.

11. ER Model

ER stands for Entity-Relationship. The ER model is a conceptual data model used to represent entities, attributes and relationships.

Main Components

  • Entities
  • Attributes
  • Relationships

12. Entities

An entity is a distinguishable real-world object about which data can be stored.

Examples

  • Student
  • Teacher
  • Course
  • Employee
  • Department

Entity Set

An entity set is a collection of similar entities.

Example:

All students of a college together can form a Student entity set.

13. Attributes

An attribute is a property that describes an entity.

Example

For a Student entity:

  • RollNo
  • Name
  • Age
  • Course
  • Address

Types of Attributes

Type Meaning
Simple Attribute Cannot be meaningfully divided further.
Composite Attribute Can be divided into smaller components.
Single-Valued Attribute Normally has one value for an entity.
Multi-Valued Attribute Can have multiple values.
Derived Attribute Can be calculated from other attributes.
Example:

DateOfBirth can be used to derive Age.

14. Relationships

A relationship represents an association between entities.

Example

STUDENT
↓
ENROLLS
↓
COURSE

Here, Student and Course are entities and Enrolls is the relationship.

Cardinality

Type Meaning
One-to-One (1:1) One entity is associated with one entity.
One-to-Many (1:N) One entity can be associated with many entities.
Many-to-One (N:1) Many entities can be associated with one entity.
Many-to-Many (M:N) Many entities can be associated with many entities.

15. ER Diagram

An ER diagram is a graphical representation of entities, attributes and relationships.

Symbol Represents
Rectangle Entity
Oval Attribute
Diamond Relationship
Lines Connections
[ STUDENT ] —— ◇ ENROLLS ◇ —— [ COURSE ]
Exam Tip:

Practice drawing ER diagrams neatly. Clearly label entities, attributes and relationships.

16. Generalization

Generalization is a bottom-up approach in which common properties of multiple lower-level entity types are combined into a higher-level entity type.

Example: 
        EMPLOYEE
        /      \
       /        \
  TEACHER     ENGINEER

Teacher and Engineer may have common properties such as EmployeeID and Name. These common properties can be represented in a higher-level Employee entity.

17. Specialization

Specialization is a top-down approach in which a higher-level entity is divided into more specific lower-level entity types.

Example: 
        EMPLOYEE
        /      \
       /        \
  MANAGER     ENGINEER

Employee can be specialized into Manager and Engineer according to their specific characteristics.

Difference:

Generalization = Bottom-up
Specialization = Top-down

18. Aggregation

Aggregation is an abstraction mechanism used to treat a relationship set and its participating entities as a higher-level entity so that it can participate in another relationship.

Example:

Suppose an Employee works on a Project and a Manager monitors that work relationship. The "works on" relationship can be treated as a higher-level object when representing the monitoring relationship.

Easy Definition:

Aggregation allows a relationship involving entities to be treated as a higher-level unit for another relationship.

19. Converting ER Diagram to Relational Tables

An ER model can be transformed into relational tables for implementation in a relational database.

Rule 1 – Strong Entity

Create one relation for each strong entity. Include its simple attributes and choose an appropriate primary key. 

STUDENT
----------------
RollNo  PK
Name
Course

Rule 2 – Composite Attributes

Break a composite attribute into its component attributes.

Address → HouseNo, Street, City

Rule 3 – Multi-Valued Attributes

A separate relation is generally created for a multi-valued attribute, along with the primary key of the original entity.

Rule 4 – One-to-One Relationship

For a 1:1 relationship, a foreign key can generally be placed in one of the participating relations, preferably where it best represents the relationship and participation constraints.

Rule 5 – One-to-Many Relationship

For a 1:N relationship, the primary key of the "one" side is usually included as a foreign key in the relation representing the "many" side. 

DEPARTMENT
-----------
DeptID PK
Name

STUDENT
-----------
RollNo PK
Name
DeptID FK

Rule 6 – Many-to-Many Relationship

For an M:N relationship, create a separate relation containing the primary keys of the participating entities as foreign keys. Together they commonly form a composite primary key. 

STUDENT
-----------
RollNo PK
Name

COURSE
-----------
CourseID PK
CourseName

ENROLLMENT
-----------
RollNo FK
CourseID FK
Important:

The exact conversion can depend on participation, cardinality and other constraints, so always check the ER diagram carefully.
